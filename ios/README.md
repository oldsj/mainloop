# Mainloop for iOS

An iPhone app for Mainloop's owner: the web app in a native shell that holds the device's keys. See
[docs/specs/ios-app.md](../docs/specs/ios-app.md) for what it does today and what is planned.

## Layout

| Path                                 | What it is                                                                                                                                                                                                                           |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `project.yml`                        | XcodeGen spec, the source of truth. The generated `Mainloop.xcodeproj`, `App/Info.plist` and `App/Mainloop.entitlements` are gitignored.                                                                                             |
| `Config/Mainloop.xcconfig`           | Placeholder bundle ID and origin, and the APNs environment per configuration. Includes `Config/Local.xcconfig` if it exists.                                                                                                         |
| `App/`                               | The shell: first run, the web view and its message handler, the approval sheet and This iPhone, in the web's theme.                                                                                                                  |
| `Tests/`                             | App tests, run on the simulator.                                                                                                                                                                                                     |
| `Packages/MainloopKit`               | Everything that doesn't need UIKit: `MainloopAPI` (the generated client) and `MainloopCore` (keys, signing, the approval flow, the shell's rules, the palette). Its tests run on macOS with `swift test`.                            |
| `Packages/MainloopKit/.../Generated` | The Swift client generated from `api/openapi.yaml`. Do not edit; run `scripts/generate-api.sh`.                                                                                                                                      |
| `Packages/APIGen`                    | Pins swift-openapi-generator, and `PrepareContract`, which rewrites a temporary copy of the contract into a form the generator reads (nullable `anyOf: [X, null]` becomes an optional `X`; integer bounds beyond Int64 are dropped). |
| `scripts/generate-api.sh`            | Regenerates the client. Add an operation to `Packages/APIGen/openapi-generator-config.yaml` first.                                                                                                                                   |
| `scripts/ci.sh`                      | What CI runs: regenerate the client (a stale committed copy is a warning on pull requests and a failure on main, with a patch artifact; see AGENTS.md), `swift test`, then the simulator build and tests.                            |
| `Design/make-app-icon.py`            | Draws the app icon from the web's mark (standard library only).                                                                                                                                                                      |

## Build

Requires Xcode 27.1 or later (the iOS 27.1 SDK is what lays the app out for iPhone Duo) and
[XcodeGen](https://github.com/yonaskolb/XcodeGen). CI runs on GitHub's `xcode-27` image.

```sh
ios/scripts/ci.sh                                      # everything CI runs
swift test --package-path ios/Packages/MainloopKit     # models and fixtures only, no simulator
```

By hand:

```sh
cd ios
xcodegen generate
open Mainloop.xcodeproj
```

The app builds with the placeholder origin and says it names no server. To run it on a phone, copy
`Config/Local.xcconfig.example` to `Config/Local.xcconfig` and set your team ID, bundle ID and
Mainloop origin. Nothing in `Local.xcconfig` is committed. To sign in, also set the Pocket ID
issuer and the app's OIDC client: a public client (PKCE, no secret) with the redirect URI
`mainloop-ios://oauth/callback`, whose id the server lists in `MAINLOOP_AUTH_DEVICE_CLIENT_ID`
(see `docs/specs/devices.md`).

### Notifications

Not yet proven on a phone. The app target carries two entitlements, generated by XcodeGen into
`App/Mainloop.entitlements`: `aps-environment` and Time Sensitive Notifications. To sign it:

- The App ID (your bundle ID) needs the **Push Notifications** and **Time Sensitive
  Notifications** capabilities in the Apple Developer portal; automatic signing then puts them in
  the provisioning profile.
- `MAINLOOP_APNS_ENVIRONMENT` sets `aps-environment` and is sent to the server with the device
  token. It defaults to `development` (the APNs sandbox) for Debug, which is what a build run
  from Xcode uses, and `production` for Release (TestFlight, App Store). Set it in
  `Local.xcconfig` only to override both.
- The server needs an APNs key for the same team and bundle ID (see
  `docs/specs/push-notifications.md`). A sandbox token works only with the sandbox endpoint.

CI builds for the simulator with no team or provisioning profile, which these entitlements
don't need there.

## iPhone Duo

Built with the iOS 27.1 SDK or later, the app fills both of iPhone Duo's displays: the outer one
(466 × 678 points) and the inner one (669 × 951, either way up), where the status bar is a column
on the right edge and leaves a right-hand safe-area inset that lasts for the whole scene.

- **No device checks.** The app reads no `UIScreen.main`, interface orientation, idiom or device
  size; layouts follow the space they get. Xcode's _app resizability_ skill found none of its
  target APIs. Its prerequisites hold: a launch screen (`UILaunchScreen`), no
  `UIRequiresFullScreen`, the SwiftUI scene lifecycle. `UISupportedInterfaceOrientations` lists
  portrait and both landscapes; the inner display ignores the list.
- **Native screens** (first run, the approval sheet, This iPhone) stay in SwiftUI's safe area and
  cap their content's width (first run at 560 points), so they read the same in every pose.
- **The web view** runs edge to edge (`ignoresSafeArea`, and the scroll view adds no insets). The
  page declares `viewport-fit=cover` and pads itself with `env(safe-area-inset-*)`, including the
  status bar's column on the right. The web app shows its desktop layout (sidebar and page) on a
  window at least 640 px on both sides, which is the inner display, and its phone layout on the
  outer one ([layout](../docs/specs/layout.md#desktop)).
- **To try it:** the _iPhone Duo_ simulator (Xcode 27.1 or later). Opening and closing it, and
  resizing a scene, are in Device Hub's window. `simctl io <device> screenConfig` only powers a
  display or changes its mode. Device Hub's resizable simulator and iPhone Mirroring (resized) are
  Apple's other two ways to test.

### The App Store's iPhone Duo badge

From Apple's [Prepare for iPhone Duo](https://developer.apple.com/iphone-duo/prepare/) page (read
in November 2026). Check it again before submitting.

- The badge shows on the product page when the version has **iPhone Duo screenshots** in App Store
  Connect.
- Sizes: the outer display at 1398 × 2034 (portrait) or 2034 × 1398 (landscape); the inner display
  at 2007 × 2853 or 2853 × 2007. PNG or JPEG, no transparency, up to 10 per size.
- From **April 2027** an app built with the iOS 27.1 SDK or later can't be submitted without
  them.
- Featuring: nominate the version in App Store Connect (**Featuring Nominations**) and say in
  _Helpful details_ that it is optimised for iPhone Duo in every pose.
- Screenshots use fictional data only: the web app's fixtures (`VITE_MSW=1`, `?seed=review`; see
  `web/src/test/msw/review-seed.ts`) or a disposable server with made-up records. `simctl io <device> screenshot
--display=<name>` writes a display at its native size; `simctl io <device> enumerate` names the
  displays.

## Release (proposed, not built)

There is no TestFlight or App Store pipeline yet. The proposal:

- **A separate workflow,** `ios-release.yml`, run by hand (`workflow_dispatch`) or on a tag
  `ios-v*` from `main`. Never on a pull request: this is a public repository, and a pull
  request's workflow must never reach a signing secret.
- **GitHub-hosted** `xcode-27` runner, as for CI. The job runs in a GitHub environment,
  `app-store`, that requires James's approval and allows only `main` and `ios-v*` tags.
- **Signing without certificates in the tree:** an App Store Connect API key (App Manager role)
  lets `xcodebuild -allowProvisioningUpdates -authenticationKeyPath …` use cloud-managed
  certificates and profiles, so no `.p12` or profile is stored anywhere. Then `xcodebuild
-exportArchive` and upload with the same key (`xcrun altool --upload-package` or the App Store
  Connect API).
- **Secrets from 1Password:** James creates the items in a vault of their own, for example `mainloop-ios-release`:
  - the API key (`.p8`, key ID, issuer ID);
  - the team ID, bundle ID, Mainloop origin, Pocket ID issuer and client.

  A read-only 1Password service account for that vault is the environment's only GitHub secret.
  `1password/load-secrets-action` (pinned by SHA) loads the items into the job, which writes
  `Config/Local.xcconfig` and the key to a temporary file and deletes both at the end. Nothing is
  echoed. The release build sets `MAINLOOP_APNS_ENVIRONMENT=production`.

- **Build number:** the run number, so every upload is unique. The version comes from the tag.
- **Screenshots** stay a manual upload until the screens settle. `fastlane deliver` or the App
  Store Connect API could upload them later.

Before the first run, James needs: an App ID with Push Notifications and Time Sensitive
Notifications, an App Store Connect app record, the API key, and the 1Password items above.

## Rules

- The API is called only through the generated client, as in `web/`.
- Fixtures, previews and screenshots use fictional data only.
- The page in the web view never gets a key, a signature or the session's token; anything signed
  is done natively (docs/specs/ios-app.md).
- No signing material in the tree or in CI logs; CI builds unsigned.
